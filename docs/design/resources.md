# roshanavi — リソース監視 (CPU・メモリ・ディスク・ネットワーク・GPU)

ノードがどれだけ CPU・メモリ・ディスク・ネットワーク・GPU を使っているかを、同じ PC の中で 1 秒ごとに測り、地図・右ペイン・「リソース」タブ・診断パネル・シナリオで見せる (Lv1)。複数の PC・コンテナをまとめて見る Lv2 は将来の課題 ([将来 (Lv2)](#将来-lv2-複数-pc複数コンテナ))。実装は `roshanavi/resources/`、API は `server_resources.py`、画面は `web/src/resources/` と `web/src/detail/NodeResources.tsx`。

![リソースタブ](../images/resources-tab.png)

## 前提: ノードとプロセスの対応づけ
ROS 2 のグラフ情報には、ノードがどのプロセス (PID) で動いているかが含まれない。そのため状況ごとに手段を変え、上から順に最初に当てはまったものを使う (`attribution.py`)。

| 状況 | 対応づけ | 精度 (UI) |
|---|---|---|
| Launcher で起動し、argv に `__node:=` があるノード | Launcher の対応づけ ([launcher.md#ノード ⇄ プロセスの対応づけ](launcher.md#launcher-p3)、`process_map.py`) をそのまま使う。`ros2 run` のラッパーではなく実行ファイルのプロセス | 確実 |
| 同じ PC の他のノード (ターミナル・シナリオ・別の launch で起動) | プロセスの argv の `__node:=` / `__ns:=` (最も深いプロセス。ラッパーも同じノードの分として数える) | 推定 |
| Launcher の時刻による推定 (起動直後に現れた名前なしノード) | Launcher の推定。プロセスまで分からなければ、その起動設定のプロセス全体の合計 (「起動設定全体」) | 推定 |
| 上のどれにも当たらない | 実行ファイル名がノード名と同じプロセスが **1 つだけ** あるとき (`demo_nodes_cpp talker` → `/talker`) | 推定 |
| composable node (コンテナ) | ノードごとには分けられない。同じプロセスのノードは「n ノードで共有」とし、値はプロセス全体 | プロセス単位 |
| 別コンテナ (PID 名前空間が別) / 別 PC | 対応づけない (地図にバッジが出ない)。Lv2 の課題 | — |

- argv の `__node:=` を Launcher の時刻による推定より先に見るのは、シナリオやターミナルが起動したノードが、たまたま直前に起動した起動設定の分と取り違えられないようにするため (実際に E2E で起きた)。
- 推定の値には UI で「推定」の印を付ける。Launcher でノード名を付けて起動すれば確実になる。
- シナリオの `resources` / `mem_growth` は、シナリオ自身が起動したプロセス (セットアップ・起動設定) の中で見つかれば確実とする (`node_probe.py`)。

## 監視対象 (Lv1)

| 対象 | プロセスごと | PC 全体 |
|---|---|---|
| CPU | CPU% (`top` と同じく 1 コア = 100%。PC 全体に対する割合も) | 全体・コアごと |
| メモリ | RSS / USS (USS は 5 秒ごと)、**増え方 (MB/分)** | 使用量・空き・スワップ |
| GPU | GPU メモリ (NVML のプロセス別情報があるとき) | 使用率・GPU メモリ・温度 |
| ディスク | 読み書きの速さ (`/proc/<pid>/io` の read_bytes / write_bytes) | data_dir のボリュームの空き (録画と同じしきい値で判定)・読み書きの速さ |
| ネットワーク | 接続先の一覧 (接続先ホスト・ポート・状態)、開始・終了のタイムライン。送受信量は取れない | 物理 NIC ごとの送受信の速さ・パケット数・エラー・取りこぼし (loopback は除く)、**UDP 受信バッファ溢れ** (`/proc/net/snmp` の RcvbufErrors / SndbufErrors) |
| その他 | スレッド数、開いているファイルの数 | — |

### 他プロセスとの切り分け
| 対象 | 切り分け | 根拠 |
|---|---|---|
| CPU / メモリ / ディスク I/O | できる (プロセス単位) | カーネルがプロセスごとに計上している (`/proc/<pid>/stat`, `smaps_rollup`, `io`) |
| GPU メモリ | できる (NVML のプロセス別情報があれば) | WSL2 やコンテナでは取れないことが多い (UI に表示) |
| GPU 使用率 | PC 全体のみ | プロセス別の使用率は GPU・ドライバ次第なので出さない |
| ネットワーク | 接続先はできる / 送受信量はできない | ソケットの持ち主は分かるが、NIC の量は全プロセスの合計 (プロセス別には eBPF などが必要) |

- PC 全体の CPU・メモリは **「ROS ノード / roshanavi 自身 / その他」の内訳** で見せる。「その他」には一覧できる中で多いプロセス名 (上位 5) を出す。「その他」の量は PC 全体から前の 2 つを引いたもので、一覧できない他のユーザー・他のコンテナ・カーネルの分も含む。メモリの内訳は RSS の合計による目安 (共有ライブラリは重複して数える)。
- **roshanavi 自身** (観測者効果の確認用) は常に別枠: サーバー本体 (`ros2 run roshanavi server` のラッパーを含む)、計測ノード、詳細計測 (トレース解析と LTTng、有効な間)、録画 (`ros2 bag`)、ビルド (colcon)、roshanavi が動かすノード (入力・変換・関数ノード)、その他の補助プロセス (ffmpeg など)。シナリオのセットアップで起動したノードは「ROS ノード」に入れる。
- 計測そのものの負荷 (サンプラーのスレッドの CPU 時間) も「リソース」タブに出す。

### メモリリークの見せ方 (`leak.py`)

**リークとは「一定の速さで、減速せずに、長く増え続けるメモリ」** と定義する。一度だけの増加 (段差)、バッファが埋まって頭打ちになる増加、一瞬のスパイクはリークではない。最小二乗の傾きだけを見る方式 (旧方式) は、窓の途中で一度だけ h MB 増えるだけで傾きが 0.3h MB/分 になり (3.3 MB の段差で警告)、段差が窓から外れると消えた。そこで「速度 v (MB/分) と、その変化 (減速しているか)」で判定する。

**判定の手順** (プロセスごと、純関数、時刻は呼び出し側が渡す):
1. 1 Hz の RSS を **1 分ごとの中央値** にして最大 6 時間 (360 点) 持つ。起動から 60 秒 (ウォームアップ) は除く。1 分に 10 サンプル未満 (計測が止まった分) は捨てる。中央値なので、一瞬のスパイクは 1 点に入らない。
2. **3 つの時間スケール (10 分 / 1 時間 / 6 時間) を同時に判定する**。各窓を 5 つの区間に分け、区間ごとの中央値 (レベル) を出し、隣り合う区間のレベルの差から区間ごとの速度 `v_i` (4 つ) を出す。
3. **揺れの幅 σ** をそのプロセス自身から推定する: 同じ長さの隣り合うレベルが、ふだんどれだけ違うか (差の MAD × 1.4826、直近の履歴で)。一定の増加は差を一様にずらすだけで MAD を広げず、段差・スパイクは外れ値として効かない。長い区間は平均されて揺れが小さくなるが、ゆっくりしたうねりは小さくならないので、短い区間 (6 分) の σ を `(6 / 区間の長さ) ^ 0.25` で縮めて安全側に見積もり、直接の推定値との大きい方を使う (長い窓は独立した区間が少なく、直接の推定は偶然小さく出るため)。下限 0.3 MB。
4. **リークの疑い** (診断パネルに出す) は、1 つのスケールで次の 3 つがすべて成り立つこと:
   - ほとんどの区間で増えている: 4 つの区間のうち 3 つ以上で、増加が `2.5 σ` を超える。
   - 減速していない: 後半の速度 ≥ 前半の速度の 0.5 倍 (かつ正)。
   - 合計の増加が `4 σ` と 3 MB のどちらも超える。
   さらに 2 分続けて成り立ったら出し、3 分続けて成り立たなくなったら消す (境目でのちらつき防止)。
5. **様子見 / 収束中** (リソースタブだけ。診断パネルには出さない): 合計の増加は本物だが (`4 σ` と 3 MB 超)、最後の区間もまだ増えている (`1.5 σ` 超) のに、手順 4 を満たさないもの (段差の直後、埋まりつつあるバッファ)。「増加中ですが、増え方は収まりつつあります (様子見)」と出す。
6. 画面には速度と継続時間を数値で出す: 「毎分 0.3 MB で 2 時間増え続けています (減速なし)」。速度は判定したスケールの窓全体の増加 ÷ 時間、継続時間は「判定した窓の長さ + 疑いになってからの経過」(少なくともこれだけ増え続けている)。複数のスケールが成り立てば、最も長いスケール (速度の誤差が小さい) を使う。

- GPU メモリにも同じ判定を使う (プロセス別の GPU メモリが取れる環境のみ)。
- 判定はプロセス単位なので、他のプロセスの影響を受けない。診断パネルに「`/detector` のメモリが毎分 0.3 MB で 2 時間増え続けています (減速なし)。メモリリークの疑いがあります」と出し、地図のノードを警告色で囲む。
- **roshanavi 自身のプロセスも判定に含める** (除外しない)。リソースタブでは常に「roshanavi 自身」の別枠に並べ、診断パネルでは「roshanavi 自身 (サーバー本体) のメモリが…」と書く。関数ノード・入力ノード・変換ノードは利用者のコードや利用者が作ったノードなので、ふつうのノードと同じ扱い。バッファが埋まる途中の増加は、上の「減速」の判定で「様子見」に回る。
- 計算量: 1 秒ごとのサンプルは 1 分バケツに入れるだけ。判定 (3 スケール) は 1 分に 1 回。プロセスあたり 360 点の履歴だけ持つ。

**検出できる速度と検出までの時間 (合成データでの実測)**

数字は推測ではなく、`test/test_leak_detector.py` の合成データ (1 Hz、基準 200 MB に直線の増加 + 揺れ) で実際に検出できた値で、テスト (`test_detection_limits`) が毎回これを確かめている。揺れは「プロセス自身の揺れ」の 3 段階で、基準のうねり (1 分ごとに更新、相関時間は約 5 分) と 1 秒ごとのばらつきの合成:
- **小** (うねり σ0.3 MB + ばらつき σ0.2 MB、おおよそ ±1 MB): 安定した C++ ノードなど
- **中** (σ2 + σ1、±6 MB): メッセージのバッファを持つふつうの Python / C++ ノード
- **大** (σ6 + σ3、±20 MB): 確保と解放を頻繁に繰り返すプロセス

各スケールを単独で動かし、8 通りの乱数で全部が 13 時間以内に検出できた最小の速度 (所要時間は 8 通りの中央値 / 最大):

| スケール | 判定できるようになる最短時間 | 揺れ 小 | 揺れ 中 | 揺れ 大 |
|---|---|---|---|---|
| 10 分 | 17 分 | 0.5 MB/分 (17 分 / 17 分) | 1 MB/分 (173 分 / 425 分) | 3 MB/分 (173 分 / 425 分) |
| 1 時間 | 59 分 | 0.07 MB/分 (76 分 / 261 分) | 0.3 MB/分 (106 分 / 416 分) | 1 MB/分 (105 分 / 347 分) |
| 6 時間 | 347 分 (約 5.8 時間) | 0.01 MB/分 (437 分 / 637 分) | 0.05 MB/分 (347 分 / 381 分) | 0.15 MB/分 (347 分 / 381 分) |

最短時間は、ウォームアップ 1 分 + 窓 (1 時間・6 時間はほぼ窓の長さ、10 分の窓は揺れの推定に 12 個以上の差が要るので 15 分分の履歴) + 確認の 1 分。最小の速度のあたりでは、窓にたまたま乗った揺れしだいで検出が遅れる (表の最大)。速度が最小の数倍あれば、最短時間で検出できる (揺れ 中: 10 分スケールは 3 MB/分で 17 分 (最大 19 分)、1 時間スケールは 1 MB/分で 59 分 (最大 60 分)、6 時間スケールは 0.07 MB/分で 347 分)。3 つのスケールの総合では、検出できる最小の速度は 6 時間スケールの値になり、一定の速さの 3 MB/分は 17 分、揺れ 中のプロセスの 0.1 MB/分は 6 時間 (347 分) 後に検出される。

**検出できる最小速度 ≈ メモリの自然な揺れ ÷ 観察時間** なので、遅いリークほど検出は遅いが、見逃さない (6 時間見れば、揺れ ±6 MB のプロセスの 0.05 MB/分 = 1 時間に 3 MB の漏れが見える)。

**誤検出しないパターン** (単体テスト):
- 一度だけの段差 (30 MB): 疑いにならない。「様子見」が 15〜30 分ほど出て、消える。
- 頭打ち: 5 分で直線的に埋まって止まるバッファ、時定数 3 分・10 分の指数的な飽和 (窓の中で十分に減速する) は疑いにならない。
- スパイク: 60 MB が 2 分、60 MB が 20 秒を 15 分おき: 疑いにならない。
- 揺れだけ (増加なし): 揺れ 小・中・大で、24 時間の実行を計 400 回 (小 100 回、中 100 回、大 200 回) 試して、疑いになったのは 0 回。
- 一定速度 (3 MB/分)・加速する増加: 検出する (加速する増加は検出後も疑いを出し続ける)。

**限界** (README にも書く):
- **RSS (実際に使っている物理メモリ) を見ている**。言語のアロケータ (glibc malloc、Python のメモリプールなど) は、解放したメモリを OS に返さないことがあり、リークでなくても RSS が減らない。その場合は「増えて止まる」形になるので多くは「様子見」で済むが、返さないまま増え続ける使い方だと疑いに見える。
- **揺れに埋もれる小さな漏れは、観察時間が短いうちは検出できない**。上の表のとおり、速度が揺れ ÷ 時間より小さい間は見えない。長い窓は独立した区間が少ないため、揺れの推定そのものも不確かで、安全側に見積もっている (速度が遅れて出ることはあっても、誤検出を優先して避ける)。
- **ゆっくり埋まるバッファは最初の 20〜40 分ほど疑いに見えることがある**: 時定数が 10 分の窓の長さ (10 分) より大きい飽和 (例: 時定数 20 分) は、10 分の窓では直線に見える。実測 (時定数 20 分・上限 60 MB) では 17 分ごろに 3〜8 分だけ疑いが出て、埋まると自然に消えた。
- **どのコードが漏らしているかは分からない**。原因の特定は各言語のプロファイラ (Python なら tracemalloc / memray、C++ なら valgrind / heaptrack など) を使う。
- **同じ PC のプロセスだけ** (他の PC やコンテナの外のノードは見えない)。
- プロセスが再起動すると履歴は最初から (新しいプロセスとして扱う)。roshanavi が再起動すると、全プロセスの履歴が 17 分以降の判定まで空になる。

### roshanavi 自身のメモリの増え方 (調査の結果)

きっかけ: 10 時間動かしたデモ環境で、roshanavi のサーバー本体が 1 時間スケールで「毎分 0.32 MB で 62 分増えた」と判定され、そのあと止まった (RSS 174 MB、最大値 = 現在値)。ノードの作成・削除、ビューア・エコーの開閉、シナリオ実行を何百回も繰り返した環境だった。**実測して、無限に増える漏れではなく、接続の出入りで積み上がって頭打ちになる増え方が主だと分かった**。調べ方と結果は次のとおり。

- **再現用の負荷** `scripts/churn_harness.py`: 起動中のサーバー (隔離したスタック) に、操作の種類ごとに **1 種類だけ** を繰り返し (ノード作成 + 起動 + 削除 4 種、エコー / 画像ビューア / `/ws/live` / リソース / ログの WebSocket の開閉、シナリオ実行、起動リストの登録・起動・停止・削除、トピック監視の切り替え、パラメータ、注入、読み取り API、何もしない)、RSS を `--sample-every` 回ごとに測って、最小二乗の傾き (**MB / 100 回**) を出す。サーバーを `ROSHANAVI_DEBUG_TRACEMALLOC=1` で起動すると、Python のヒープ (tracemalloc)・生きているオブジェクト数・スレッド・fd も測る (後述)。
- **切り分けの道具** (既定ではオフ): `ROSHANAVI_DEBUG_TRACEMALLOC=1` で起動時から tracemalloc を有効にし、`GET /api/_debug/memory` を足す (`route` と書くと tracemalloc なしで経路だけ)。`snapshot=1` で増えた確保箇所、`objects=1` で型ごとの数、`find=型名` でその型を持っているものの参照元、`collect=1` で完全 GC、`trim=1` で `malloc_trim` (RSS のうち「解放済みなのに OS に返していない」分が分かる)。Host / Origin の検査はほかの経路と同じ。変数がなければ経路自体がない。

**操作の種類ごとの増え方** (MB / 100 回、各 100 回、warm-up 15 回、4 並列。サーバー単体の RSS):

| 操作 | 修正前 | GC・圧縮なし | + アリーナ制限 |
|---|---|---|---|
| 何もしない (100 回 = 約 2.5 分) | 0.40 | 0.36 | 0.43 |
| 読み取り API を 9 本 | 1.0 | 1.3 | 0.75 |
| 入力ノード作成・削除 | 1.2 | 0.86 | 1.4 |
| 変換ノード | 0.28 | 0.21 | 0.06 |
| 関数ノード | 0.68 | 0.67 | 1.4 |
| クラスノード | 0.83 | 1.0 | 0.81 |
| **エコー WS の開閉** | **7.2** | 2.4 | 0.58 |
| **画像ビューア WS の開閉** | **9.0** | 4.0 | 1.8 |
| `/ws/live` の開閉 | 1.5 | 0.0 | 0.41 |
| `/ws/resources` の開閉 | 1.7 | 0.15 | 0.08 |
| **ログ WS の開閉** | **9.6** | 1.7 | 1.8 |
| 起動リストの登録・起動・停止・削除 | -2.2 | 0.03 | 0.16 |
| トピック監視の切り替え / パラメータ / 注入 | 0.00 / 0.12 / 0.06 | -1.2 / 0.2 / -0.01 | 0.02 / 0.10 / 0.09 |
| シナリオ実行 | 0.20 | 0.76 | 1.2 |
| 全部を順に実行した後の RSS (110 MB から) | 157.4 MB | 128.3 MB | 124.7 MB |

全対策 (次の「対策」の全部) を入れて 500 回ずつ測り直すと (MB / 100 回、warm-up 30 回、最初の 100 回の立ち上がりを含む): 画像ビューア 0.75、エコー 0.17、クラスノード 0.70、入力ノード 0.15、関数ノード 0.40、起動リスト 0.17。エコーを 500 回繰り返しても RSS は 119.3 → 120.3 MB、Python のヒープは一定。残りの増加は warm-up の延長 (スレッドプールが 18 → 27 本まで増える、fd が 113 → 117 で止まる、起動リストのログのリングバッファが埋まる) で、回数に比例して増え続けるものは見つからなかった。

**原因** (上の表で大きかった順):

1. **WebSocket の接続オブジェクトが、完全 GC (世代 2) が走るまで残る**。接続 (uvicorn + websockets) は循環参照で、開いている間に最古の世代へ移る。CPython の完全 GC は「前回から増えた長寿命オブジェクトが全体の 25 % を超えたとき」だけなので、長寿命オブジェクトが 10 万個ある roshanavi では数百接続ぶんの残骸が溜まってから初めて掃除される。しかも WebSocket の **permessage-deflate は接続ごとに zlib の圧縮器 (約 150 KB) を持つ**ため、エコー 100 回 (= 100 接続) で Python のヒープが +15 MB (tracemalloc。`PerMessageDeflate` 104 個が生きていて、`gc.collect()` で 4153 個を回収して -15 MB)。掃除された後のメモリは再利用されるが、OS には返らない。つまり **接続を何百回も開閉すると、数十 MB 増えて頭打ちになる**。これが「止まる増加」の正体。
2. **glibc のアリーナの断片化**。glibc はメモリを確保するスレッドごとに独立した領域 (アリーナ、最大 コア数 × 8 個) を作る。roshanavi は Web サーバーのスレッドプール・rclpy の executor・サンプラーが別々のスレッドで確保・解放するので、あるアリーナで解放した領域を別のスレッドが使えず、RSS が階段状に上がって戻らない。GC と圧縮の修正だけを入れた時点での比較は、500 回のクラスノード作成・削除で既定 +10 MB・アリーナ 2 つ +1.5 MB、画像ビューア 500 回で +5 MB と +0.8 MB。サーバー本体のアリーナ領域は 45 個 (144 MB) → 1 個になる。**ほかの対策を全部入れたあとの差は小さい**: 6 種類 × 500 回 (計 3000 回) で RSS +6.9 MB (2 つ) と +9.8 MB (既定の上限 192)。
3. **小さな本物の漏れ 3 つ** (どれも 1 回あたり数百バイト):
   - rclpy (Jazzy) は、タイマー・購読・クライアント・イベントハンドラーを作るたびに callback group の `entities` 集合へ `weakref` を足し、**壊したあとも消さない**。購読の作成・削除 1 回で約 300 バイト、1000 回で約 1000 個の死んだ参照が残った。
   - `LifecycleService` の状態キャッシュはノード名ごとに足すだけで、消えたノードの分を消していなかった。
   - 逆引き DNS のキャッシュ (`ReverseDns`) は期限切れの項目を消さず、上限もなかった。

**漏れではなかったもの** (確かめた): 読み取り API を 5400 回呼んでも Python のヒープは +0.4 MB (起動リストのログのリングバッファが埋まっただけ)。ブラウザのタブを開いたまま (`/ws/live` + `/ws/resources` + `/ws/echo` + `/ws/scenarios` を 10 分) も Python のヒープ +0.5 MB、オブジェクト数は一定。起動リストの削除 (ログのリングバッファは 1 件 5000 行 ≈ 1 MB が上限、削除で解放)。`process_map` / `diag_history` / リソースの履歴・リーク判定の系列 (消えたプロセスは掃除される) / トレースのモデル (別プロセス) / ゴミ箱 (最大 8 件・15 秒) は、すべて上限か掃除があることを読んで確認した。fd とスレッド数は増え続けない (スレッドプールが 18〜21 本で頭打ち)。

**対策** (`ros2_ws/src/roshanavi/roshanavi/`):
- `main.py`: WebSocket の圧縮を切る (`WS_PER_MESSAGE_DEFLATE = False`。localhost では得るものがない)。起動の最初に `malloc_tuning.limit_malloc_arenas()` (`mallopt(M_ARENA_MAX, 2)`。利用者が `MALLOC_ARENA_MAX` を設定していればそれを優先)。
- `gc_janitor.py`: 60 秒ごとに完全 GC を 1 回 (housekeeping から)。閉じた接続の残骸が溜まる量を、最大 1 分ぶんに抑える。完全 GC は約 11 万個のオブジェクトを全部たどって 1 回 約 50 ms かかる (GIL を持ったままなので注入のペースに引っかかる) ため、起動が終わった時点で `gc.freeze()` して起動時のオブジェクトを GC の対象から外す (1 回 約 1 ms)。
- `ros_runtime.py`: 購読・クライアント・タイマー・パブリッシャーを壊すとき、すでに無くなったエンティティの `weakref` を callback group から消す (実行中のコールバックは強い参照を持つので影響しない)。
- `lifecycle.py` / `resources/connections.py`: 期限切れの状態キャッシュを毎回消す、逆引き DNS のキャッシュに上限 (1024) を付ける。

**検出器は変えない**。1 時間スケールで出た疑いは、判定の定義 (一定の速さで減速せずに増える) どおりの正しい動きだった。「連続する 2 つの窓で増えていること」を求めると、すべての本物のリークの検出が 2 倍遅れる一方、今回の原因 (上の 1・2) は直したので、同じ形の「止まる増加」は 1 分ぶんの GC 残骸と階段 1〜2 段に縮んだ。RSS だけを見ている以上、アロケータが返さないメモリは区別できない (上の「限界」のとおり)。診断の文に出る速度・継続時間と、リソースタブの履歴を見て、止まったかどうかを判断してもらう。再現は `scripts/churn_harness.py` (使い方はファイル先頭) で、`ROSHANAVI_DEBUG_TRACEMALLOC=1` のサーバーに対して `--ops echo,view --iterations 200 --snapshots`。

### ネットワークの注意点 (`connections.py`)
- **NIC の監視は「PC の外との通信」の監視**。同じ PC 内の ROS 通信は loopback または共有メモリを通り、物理 NIC には現れない (PC 内の量はトピックの帯域で見る、[map-and-traffic.md#traffic](map-and-traffic.md#traffic))。
- **監視できるのは roshanavi が動いている PC だけ** (UI に明記)。他の PC の NIC や UDP の状態は見えない。コンテナの中では `/proc/net/*` はそのコンテナのネットワークの分だけ。
- **接続先**: 監視しているプロセス (ROS ノードと roshanavi 自身) のソケットを 1 秒ごとに調べる。`psutil.net_connections` と同じ情報源 (`/proc/net/{tcp,tcp6,udp,udp6}` と各プロセスの `/proc/<pid>/fd` のソケット) だが、表は 1 回だけ読み、監視しているプロセスの fd だけを見る。表の読み直しはソケットの集合が変わったときと 5 秒ごと (TCP の状態の変化) に限る。プロセスの fd のリンク先も、fd の番号の集合が変わったときと 5 秒ごとにだけ読む。
  - 一覧に出すのは接続先のあるもの (LISTEN 以外の TCP と、接続済みの UDP)。DDS の未接続の UDP ソケットは数だけ。リソースタブでは「この PC 内」(loopback) の接続は既定で隠す (ブラウザと roshanavi の WebSocket などで埋まるため)。
  - 接続の開始・終了をタイムラインに出す (直近 300 件)。ポーリングなので 1 秒未満の短い接続は取りこぼすことがある (確実に捕まえるには eBPF / conntrack のイベントが必要。将来の選択肢)。
  - 接続先のホスト名は逆引きする。逆引きは専用のスレッド 2 本で行い、結果をキャッシュする (成功 10 分、失敗 5 分、待ちは 64 件まで)。サンプラーは待たない (分かるまでは IP アドレス)。`--no-reverse-dns` で止められる。
- **通信内容は見ない**: パケットキャプチャ (root が必要) も TLS の中継もしない。接続先・時刻・状態のメタデータのみ。ROS のメッセージの中身はトピックのエコーで見る。
  - 理由: 通信を中継して覗く機能が本体に入っていると、企業のソフトウェア承認やセキュリティ審査で導入を拒否されたり、EDR に検知されたりするおそれがある。企業内でも使えることを優先する。
  - 将来の選択肢 (優先度最低): 本体とは別パッケージ (`roshanavi_inspector`、既定では入らない) として、Launcher で起動したノードに限りローカルのプロキシを経由させる。代替案は、開発者が自分のノードに組み込む小さなロギング用ヘルパー (API 呼び出しの要約を `/roshanavi/api_log` に流す)。
- **UDP 受信バッファ溢れの診断** (`diagnose.py`): 直近 60 秒に RcvbufErrors が増えていて、かつ大きなメッセージ (平均 64 KiB 以上) のトピックで取りこぼし (`dropped` / `drop_ratio`) が出ていれば、「受信バッファ不足の可能性。`net.core.rmem_max` の引き上げを検討してください」と警告する (ROS 2 で大きなデータを扱うときの典型的なつまずき)。大きなトピックの取りこぼしが無ければ診断には出さず、リソースタブの件数 (直近 60 秒の増加は橙色) だけで見せる (起動が重なるときなどにも増えるため、手の打ちようのない案内を出し続けないように)。重い型を監視していない (`--monitor-heavy` なし) と、画像などの取りこぼしは分からないので、警告は出ない。

### ディスクの安全装置
- 録画と同じしきい値 (`DiskThresholds`: 既定は 1 GB または 5% で警告、256 MB または 1% で停止。`--record-*-free-*` で変更) で data_dir のボリュームを判定し、リソースタブに「十分 / 少ない / 不足」と出す。警告・不足は診断パネルにも出す (録画中かどうかも添える)。録画の自動停止は録画の機能が行う ([input-and-media.md#録画](input-and-media.md#録画-p4))。
- data_dir がブロックデバイスでない場合 (tmpfs など) は、ボリュームの読み書きの速さは「取れません」と出す。

### GPU (`gpu.py`, 任意)
- `pynvml` (`python3-pynvml`) と NVIDIA のドライバがあれば、GPU ごとの使用率・メモリ・温度と、プロセスごとの GPU メモリを取る。どちらかが無ければ監視しない理由を UI に出す (他の機能は普通に動く)。
- WSL2 では GPU 全体の値は取れるが、プロセスごとの一覧が空のことが多い (「プロセスごとの GPU メモリは取れません」と表示)。Docker では `--gpus` を付けたときだけ GPU が見え、NVML が返す PID はホストの PID なのでコンテナの中のプロセスと一致しない。

## 仕組み (`resources/`)
- `service.py`: 1 Hz のサンプラー。**専用のスレッド** で動き、asyncio のイベントループと rclpy の executor のスレッドでは何もしない。1 回ごとに不変のスナップショットを作り、ロックの下で差し替える。API はそれをコピーして返すだけ。必要な ROS 側の情報 (グラフのノード、Launcher の対応づけ・起動設定・役割、計測ノード・トレース・録画の PID、トラフィック) は `Lab._resource_context` から 1 秒に 1 回読む (トラフィックは UDP の溢れがあったときだけ)。
- `procs.py`: `/proc/<pid>/stat` を 1 プロセス 1 回読む (親・名前・CPU 時間・スレッド・起動時刻・RSS)。argv は最初の 1 回だけ。I/O・USS・fd は監視しているプロセスだけ。psutil の `process_iter` は 1 プロセスあたり約 5 回ファイルを開き、70 プロセスで 1 コアの 3% を使ったので置き換えた。
- `attribution.py` (対応づけと内訳の区分)、`summary.py` (API の形)、`leak.py`、`host.py` (CPU はコアごとの `cpu_times` の差分。`psutil.cpu_percent` は他の呼び出しと状態を共有するので使わない)、`snmp.py`、`connections.py`、`gpu.py`、`diagnose.py`。
- 計測の負荷 (実測、Docker、24 コアの PC): デモ構成のラボ (13 プロセス、詳細計測あり) で 1 回 約 2 ms (1 コアの 0.2%)。約 50〜70 プロセスをすべて詳しく見る最悪の場合で 1 回 中央値 5.5 ms、起動直後の新しいプロセスの読み込みを含む直近 10 回の平均で 1 コアの 1.5〜1.7%。テスト `test_sampler_stays_light_with_fifty_processes` は 4% 未満を確かめる (目標 2% 未満の 2 倍の余裕)。重かったのは fd ごとの `readlink` (詳細計測の LTTng は数百の fd を持つ) で、fd の番号の集合が変わったときと 5 秒ごとにだけ読むようにした。

## 権限とプライバシー
- 読むだけ: `/proc` のファイルを読むだけで、シグナル・ptrace・パケットキャプチャはしない。
- **自分のユーザーのプロセスだけ** を一覧する。他のユーザーのプロセスは CPU・メモリの一部が読めても一覧に出さない (PC 全体の値にだけ含まれる)。root で動いているとき (Docker のコンテナなど) は、そのコンテナ (PID 名前空間) のすべてのプロセスを出す。画面にどちらかを明記する。
- 接続の一覧は接続先と状態だけで、中身は見ない。逆引きは接続先の IP を DNS に問い合わせる (`--no-reverse-dns` で止められる)。
- 詳細: [security.md](security.md#他人のプロセスに触らない)。

## busy_demo で確かめる
`examples/busy_demo` (MultiThreadedExecutor の空回り、[measurement.md#CPU が高い](measurement.md#cpu-が高い-multithreadedexecutor-の空回り)) を開いて `busy_demo_driver` と `multi_default` を起動すると、地図の `/busy_multi_default` が赤く光り `CPU 90% 前後` と出る。`multi_off` に替えると数 % になる。監視で見た値 (Docker、24 コア、テストの実測): multi + default 93%、multi + off 8% (シナリオの `for` の間の平均では 85〜87% と 7〜8%)。

## シナリオ連携
- `resources: {node, cpu_max, mem_max_mb, for}`: `for` 秒間 (既定 5) の **CPU の平均** (CPU 時間 / 経過時間、1 コア = 100%) が `cpu_max` 以下、**RSS の最大** が `mem_max_mb` 以下 (どちらか片方でもよい)。一瞬の負荷で落ちないよう平均で判定し、0.5 秒ごとの最大値も結果に出す。
- `mem_growth: {node, max_mb_per_min, for}`: `for` 秒間 (10 秒以上) の RSS の傾き (最小二乗、MB/分) が上限以下。ウォームアップは無いので、起動直後の確保を除くなら前に `wait` を置く。途中でプロセスが入れ替わった (再起動した) ら判定しない。
- ノードはこの PC の、同じユーザーのプロセスとして見つかる必要がある。見つからなければ「プロセスが見つかりませんでした」で失敗する。CLI (サーバーなし) でも argv から探して動く。詳細: [scenarios.md](scenarios.md#ステップの種類)。例: `examples/scenarios/busy_cpu.yaml` (multi + off が `cpu_max: 40` を満たす。`qos_events: 'default'` にすると CPU 1 コア近くになり失敗する)。

## 将来 (Lv2: 複数 PC・複数コンテナ)
- 各マシンで `ros2 run roshanavi agent` を動かし、プロセスごとの統計を `/roshanavi/host_stats` (独自 msg) で publish する。roshanavi 本体はこれを集約し、ホストごとに表示する。別コンテナ・別 PC のノードの対応づけもエージェント側で行う。
- 発展 (任意): Launcher が起動するノードを専用の cgroup (`systemd-run --user --scope` 等) に入れると、孫プロセスまで含めて CPU・メモリ・I/O を正確に合算できる。systemd が使えない環境では今と同じくプロセスツリーの追跡で代替する。
- 短い接続を取りこぼさない接続の監視 (eBPF / conntrack)。
