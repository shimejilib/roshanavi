# 地図の上での配線・言葉の総点検・pub/sub の 1 枚絵 (#47)

目標: **pub/sub だけ知っていれば、地図の上で線をつないでロジックを書くだけ**でノードを作れるようにする。トピック名を文字で打たない、型を意識しない。あわせて、画面の言葉を 1 つの用語集にそろえ (§4)、pub/sub の仕組みを 1 枚の絵で示す (§5)。画面の細部は [ui.md#実装メモ (地図の上での配線)](ui.md#実装メモ-地図の上での配線-47)、使い方は [guide/wiring.md](../guide/wiring.md)。

## 1. 体験
1. 地図の上で「＋ 関数・クラスノードを作る」(またはひな形・既存のモジュールから関数・クラスを選ぶ)。トピックは空のままでよい (「トピックは地図で線を引いてつなぐ」ボタンで全部空にできる)。
2. ノードが地図に置かれ、入力 (引数・処理メソッドの引数) と出力 (戻り値) が **つなぎ口** として出る。`def convert(text: str) -> str` なら左に `text · 文字列`、右に `戻り値 · 文字列`。クラスは処理メソッドごとにつなぎ口、操作メソッド (reset など) はノードの上のボタン。
3. **トピック (楕円) から入力口へドラッグ**すると、そのトピックを購読する (トピックにマウスを乗せると右に出る「＋」の取っ手から引く。入力口からトピックへ引いても同じ)。
   - データの種類が合わない組み合わせは、引いている間に「文字列の入力口に、画像のトピックはつなげません」と出し、離しても保存しない。変換できる組み合わせ (整数 → 小数など) はつなぎ、「整数を小数として渡します。」と出す。
4. **出力口から空いているところへドラッグ**すると、新しいトピックを作る。名前は `/<ノード名>/out` (クラスはメソッド名または dict のキー) を提案し、その場で直せる。既存のトピックへ引くとそこへ送る (種類が合う場合だけ)。別のノードの入力口へ引くと、出力口のトピック (無ければ新しく作る) を通してつなぐ。
5. つないだノードは数秒で再起動して動き出し、線の上をデータが流れる (既存の流れのアニメーション)。出力口にマウスを乗せると、呼ばれ方と最新の値が見える。
6. 線をクリックすると「線を外す (Delete)」「つなぎ替える…」が出る。つなぎ替えは、つなぎ口からもう一度引いても同じ。

## 2. 呼ばれ方の表示
`wiring/timing.ts` (文) と `wiring/CallTiming.tsx` (図)。関数・クラスの作成画面 (呼び出し方の下、メソッドごと) と、つなぎ口のツールチップに出す。
- 入力口が 1 つ: 「この入力が届くたびに呼ばれます」
- 入力口が 2 つ以上: 「どれかが届くたびに、全部の最新の値で呼ばれます」/「a が届いたときだけ、b の最新の値と一緒に呼ばれます」と「全部の入力が 1 回届くまでは呼ばれません」。図は入力ごとに実線 (届くと呼ぶ) か破線 (最新の値を使うだけ)。図の下のラジオで結合ルール (`trigger`) を切り替えられる。つながっていない入力はきっかけにできない。
- 入力口なし: 「10 Hz で呼ばれます」(周期は「呼ぶ頻度 (Hz)」で編集)。
- 変換ノード「届くたびに変換して送ります」/「届いたものを、そのまま送ります」、入力ノード「2 Hz で送ります」「起動したときに 1 回送ります」など。

## 3. 実装
**つなぎ口のモデル** (`web/src/wiring/ports.ts`、純関数): `/ws/live` のターゲット (仕様つき) と地図のノード (`target_id` で対応づけ) から作る。対象は roshanavi が動かす関数 (`function`)・クラス (`class`)・変換 (`transform`)・入力 (`dummy`) ノードだけ。引数名は `GET /api/functions/module` の静的な一覧から取る (`useArgNames.ts`、モジュールごとに 1 回。取れなければ「入力 1」)。地図にいない (止まっている) ノードには出さない。

**保存の形式は増やさない**: 線は、そのノードの仕様の中のトピック名そのもの (プロジェクトファイルの `functions:` / `classes:` / `transforms:` / `dummies:` と同じ)。`wiring/edit.ts` が仕様を書き換えた新しいコピーを作り (元は変えない)、既存の `PUT /api/functions|classes|transforms|dummies/{id}` で保存する。新しい API は作っていない。
- **つながっていない口** = トピック名が空 (`''`) の口 (関数・クラスノードだけ)。バックエンドの仕様の検査はこれを許し (空の口は重複・自己ループの検査から外し、`trigger` にはできない)、ノードはそこを購読も送信もしない。出力がつながっていないときも関数は呼ばれ、戻り値は送らずに `skipped` に数える。コードの書き出し (`export-code`) は全部の口がつながっているときだけ (409 `unwired_ports`)。変換・入力ノードの口は外せない (つなぎ替えだけ)。
- 種類の扱い: 既存のトピックにつなぐと、その型を口の `type` に書く (例: Lyrical の `/chatter` は `example_interfaces/msg/String`)。新しいトピックなら `type` を消して種類の既定の型にする。整数のトピックを小数の入力口につなぐと、口は `kind: float` のまま `type: std_msgs/msg/Int64` になり、受け取った値を `float()` で渡す (`data_kinds.accepts` / `resolve(..., receiving=True)`)。整数を返す出力口を小数のトピックにつなぐと、口の種類をトピックの種類 (小数) にし、送るときに変換する。変換ノードは作ったときの型と同じトピックにだけ、入力ノードは同じ種類のトピックにだけつなぎ替えられる (型を変えるには設定画面)。
- 断る理由: 種類が合わない・小数点以下が失われる (小数 → 整数)・専用の型が違う・自分の出力を自分の入力につなぐ・同じトピックを 2 つの入力口につなぐ・別のメソッドがもう送っているトピック・名前が不正。

**種類の互換性の規則は 1 つ** (`roshanavi/data_kinds.py` の `wire_compat` / `CONVERSIONS` / `REFUSALS` と、同じ規則の `web/src/wiring/compat.ts`): 送る側 (トピック・出力口) と受ける側 (入力口・トピック) の種類が同じなら `same`、`int → float` / `string → json` / `json → string` は `convert` (注記つき)、それ以外は `refuse` (`float → int` は「小数点以下が失われるため」、専用の型どうしは型が同じときだけ)。どちらかが分からない (まだ無いトピック) なら `same`。両方を同じ表 `ros2_ws/src/roshanavi/test/data/wire_compat_cases.json` で検査する (pytest `test_wiring.py`、vitest `compat.test.ts`)。`GET /api/data-kinds` は `conversions` も返す。

**反映は再起動 (決定)**: 保存のあと、動いていればノードを再起動する (`POST /api/targets/{id}/restart`)。関数・クラスノードの実行ファイルには、動いたまま購読や送信先を変える口 (制御用の通信路) が無いため。足すと新しい通信路と、その検査・テストが要り、得られるのは 1〜2 秒の短縮と状態の保持だけなので見送った。画面には「ノード wire_fn を再起動して反映しています (数秒で線が変わります)」、クラスノードでは「クラスの状態は最初からになります」と出す (つなぐ前の確認画面にも書く)。保存した仕様は、地図の情報が追いつくまで画面の側で覚えておき (`useWiring.withSaved`)、続けて別の口をつないでも古い仕様で上書きしない。

**外部・ランチャーのノード**: つなぎ口を出さない (どのトピックを使うかがコードの中で決まっているため)。そのノードに線を落とすと「/talker は、どのトピックを使うかがコードの中で決まっているノードです (…)。このノード自体はつなぎ替えられないので、そのトピック (楕円) に線を引いてください」と出す。そのノードのトピックは、線の始点・終点として使える。

**描画と操作** (`web/src/wiring/PortOverlay.tsx`): つなぎ口は cytoscape の上に重ねた本物のボタン (Tab で選べ、読み上げ用の名前つき)。位置は cytoscape が描くたびに (1 フレーム 1 回) ノードの描画位置から計算し直す (React の再描画はしない)。つなぎ口のあるノードは口の数と名前に合わせて大きくし (`graph/model.ts portBoxWidth / portBoxHeight`)、線の端を口の位置に置く (`source-endpoint` / `target-endpoint`)。名前はズームに合わせて縮み、小さすぎるときは点だけにする。引いている線は SVG、離した先は cytoscape の要素の矩形とつなぎ口の要素で判定する (`wiring/drop.ts`)。

**線を引くライブラリ (決定: 自前)**: cytoscape-edgehandles 4.0.1 (MIT) を確認したが、2021-07 から更新がなく、線を「ノードとノード」の間にしか引けない (ノードの中の口がない)、キーボード操作・読み上げがない、離した先の理由つきの判定や「空いているところで新しいトピック」がない。必要なのは口の当たり判定と 1 本の仮の線だけなので、依存を増やさず約 400 行で実装した ([dependencies.md](../project/dependencies.md))。

**キーボードと読み上げ**: つなぎ口は「wire_fn 入力口 text (文字列)、/chatter につながっています。Enter でつなぐ先を選びます。Delete で線を外します。」と読まれる。Enter (またはクリック) でつなぐ先の一覧 (`WireDialog.tsx`、`role=listbox`): ↑↓ で選び、つなげないトピックは灰色で理由つき (選べない)、出力口なら先頭に「新しいトピックを作って送る」(名前を直せる)、つながっていれば最後に「この線を外す」。Enter で確認画面、もう一度 Enter でつなぐ。Esc で戻る・閉じる。再起動でつなぎ口がいったん消えても、フォーカスは同じ口に戻る。手順は純関数 (`wiring/keyboard.ts`) で、vitest で検査する。

## 4. 言葉の総点検 (用語集)
**方針 (決定。#47 の「平易な言葉を先に・ROS の用語を括弧で添える」をやめた)**: ROS の**公式の用語をそのまま**、画面・チュートリアル・利用ガイド・README・サーバーが画面に返す文のすべてで使う。「1 つの概念に 1 つの名前」にする。理由は、利用者が ROS の資料、`ros2 topic ...` などのコマンド、エラーメッセージ、検索結果と画面を突き合わせられなければならないため。言い換えた言葉 (「チャンネル」「設定値」など) は、資料を読んだときに別のものに見えて、かえって混乱させる。

**用語集は 1 か所** (`web/src/i18n/glossary.ts`): 用語 (`ros`)・1 行の説明 (`explain`)・使ってはいけない昔の言葉 (`avoid`) を、日本語と英語の同じ構造で持つ。平易な説明は次の 3 か所だけに置く: ① 用語の ⓘ / 用語の上にマウスを置いたときの説明 (`<Term>`、`term.*`。用語集から作る)、② pub/sub の 1 枚絵 (§5)、③ 利用ガイドの用語集 ([getting-started.md](../guide/getting-started.md#用語集))。API やデータの名前 (キー・コード・型名・コマンド) は変えない。

| 用語 (画面の言葉) | 以前の言葉 (使わない) | 説明 (ⓘ・用語集) |
|---|---|---|
| ノード | ノード (変えない) | 処理の箱。データを受け取り、処理して、送り出す 1 つのプログラム |
| トピック | チャンネル | 名前の付いたデータの通り道 |
| パブリッシャー / サブスクライバー | 送信側 / 受信側 | トピックにデータを送る側 / 購読して受け取る側のノード (の口) |
| QoS | 届け方の設定 | 確実に届けるか、後から来た受信側にも渡すか、などの約束 |
| パラメータ | 設定値 | ノードの設定値 (周期、しきい値など) |
| パラメータファイル | 設定値のファイル | パラメータをまとめて書いた YAML ファイル |
| launch ファイル | 起動セット | 複数のノードを、パラメータごとまとめて起動するファイル |
| メッセージ型 | データの形 | トピックに流すデータの形 (roshanavi ではデータの種類を選べば決まる) |
| リマップ | 名前の付け替え | ノードの中で決まっている名前を起動時に変えること |
| 名前空間・パッケージ・ワークスペース・実行ファイル・ライフサイクルノード | 変えない | 説明だけ用語集に置く |

- **パブリッシャー / サブスクライバーと送信側 / 受信側 (判断)**: ROS の役割そのものに名前を付けるとき (ⓘ の説明・1 枚絵・見出し) は「パブリッシャー」「サブスクライバー」を使う。文の中の「送る側 / 受け取る側」という向きの言い方 (「送信側と QoS が合いません」、トラフィックの「送信元」) は、概念の名前ではなく向きを表す言葉として残す。
- **音声の「チャンネル数」と「データの形式」**は ROS の用語の言い換えではないので、そのまま残す (検査の対象外)。
- **適用の結果**: __COUNTS__
- **検査** (`i18n/glossary.test.ts`): 昔の言葉 (`avoid`) が、ⓘ の説明 (`term.*`) 以外のすべての UI の文言と、`web/src` のソース (テストを除く) に出ないことを調べる (`` `コード` `` は除く)。サーバー側は pytest `test_wording.py` が同じ言葉を調べる。
- チュートリアルの文言と利用ガイド (`docs/guide/`) も同じ言葉にした。

## 5. pub/sub の 1 枚絵
`web/src/wiring/PubSubPrimer.tsx`: 外部のファイルを使わない SVG と HTML の 1 枚。「ノード (処理の箱) が、名前付きのトピックにパブリッシュ (送る)・サブスクライブ (購読する)」の絵 (パブリッシャー A・B → `/chatter` → サブスクライバー C・D) と、3 点だけ:
1. パブリッシャーとサブスクライバーは、お互いを知らない。
2. 出会う手がかりは、トピックの名前だけ (1 文字違えば届かない)。
3. 1 つのトピックに、何人でも送れて、何人でも受け取れる。

最初のチュートリアル (画面の見方) の 2 つ目の手順で地図の上に出し、地図の凡例の「しくみの 1 枚絵」からいつでも開ける (Esc・× で閉じる)。色は本体の色の変数に従う (ライト・ダーク)。

## 7. 制約・今後
- 反映は再起動 (数秒、クラスの状態は最初から)。動いたまま購読を変える口は作っていない (§3)。
- 止まっているノードにはつなぎ口が出ない (地図にいないため)。設定画面でつなぐ。
- 新しく置かれたノードが地図の外に出ることがある (地図は位置を保つため自動で全体表示しない)。「全体を表示」で見える。
- 操作メソッドのトピック (`/<ノード名>/reset`) の線は、ボタンではなくノードの縁に付く。
