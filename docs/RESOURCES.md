# roshanavi — CPU・メモリ計測の設計メモ (P8, 優先度低)

P2 完了後に DESIGN.md へ統合する。

## 前提
ROS 2 のグラフ情報には、ノードがどのプロセス (PID) で動いているかが含まれない。そのため、ノードとプロセスの対応づけは状況ごとに異なる手段をとる。

| 状況 | 対応づけ | 精度 |
|---|---|---|
| Launcher で起動したノード | 起動時の PID とその子プロセス (launch が起動するプロセスを含む) | 正確 |
| 同じ PC の他のノード | プロセスの cmdline (`__node:=`、`--ros-args`、実行ファイル名) から推定 | 推定 (UI に明示) |
| composable container | ノード単位には分けられない。コンテナ単位で表示する | プロセス単位まで |
| 別コンテナ (PID 名前空間が別) / 別 PC | Lv2 の計測エージェントで対応 | エージェント次第 |

## 監視対象 (Lv1 で全て対象)

| 対象 | プロセスごと | PC 全体 | 主な目的 |
|---|---|---|---|
| CPU | CPU% (コア数換算も表示) | 全体・コア別 | 処理落ちの原因特定 |
| メモリ | RSS / USS、**増加傾き (MB/分)** | 使用量・空き・swap | **メモリリーク検出** |
| GPU | GPU メモリ (NVML 対応時) | 使用率・GPU メモリ・温度 | 認識系ノードの負荷とリーク |
| ディスク | 読み書き速度 (bytes/s、io_counters) | data_dir のあるボリュームの空き容量・I/O 速度 | bag 録画によるディスク逼迫、I/O 待ち |
| ネットワーク (**外部通信**) | 接続先の一覧: プロセスごとのソケット (接続先ホスト・ポート・状態、psutil `net_connections`)。送受信量は取れない | 物理 NIC ごとの送受信速度・パケット数・エラー・ドロップ (loopback は除外)、**UDP バッファ溢れ** (`/proc/net/snmp` の RcvbufErrors / SndbufErrors) | PC の外との通信 (外部 API 呼び出し、他 PC の ROS ノードとの DDS 通信) の監視、DDS の取りこぼし原因の特定 |

### 他プロセスとの切り分け

| 対象 | 切り分け | 根拠 |
|---|---|---|
| CPU / メモリ / ディスク I/O | **できる** (プロセス単位) | カーネルがプロセスごとに計上している (`/proc/<pid>/stat`, `status`, `io`) |
| GPU メモリ | できる (NVML 対応環境) | NVML のプロセス別 GPU メモリ。※WSL2 ではプロセス別情報が取れない場合がある |
| GPU 使用率 | 部分的 | プロセス別の使用率は GPU・ドライバ次第。取れない場合は GPU 全体の値のみ |
| ネットワーク | 接続先は**できる** / 送受信量は**できない** | ソケットの所有プロセスは分かる。NIC の送受信量は全プロセスの合算で、プロセス別には eBPF 等が必要 |

- PC 全体の値は **「ROS ノード (対応づけ済み) / roshanavi 自身 / その他」の内訳**で表示する。「その他」には上位のプロセス名 (例: ブラウザ、コンパイラ) を出し、外乱の原因が分かるようにする。
- roshanavi 自身の負荷も別枠で常に表示する (観測者効果の確認用)。
- ネットワーク (外部通信) は NIC 合計と、プロセスごとの接続先一覧を並べて表示する。「どのノードがどこと通信しているか」(例: `/llm_bridge` → `api.example.com:443`) は分かるが、そのノードが何バイト送ったかは分からない。
- **メモリリーク判定はプロセス単位なので、他プロセスの影響を受けない** (最重要のユースケースは確実に成立する)。
- 発展 (任意): Launcher が起動するノードを専用の cgroup (`systemd-run --user --scope` 等) に入れると、孫プロセスまで含めて CPU・メモリ・I/O を正確に合算できる。systemd が使えない環境では PID ツリーの追跡で代替する。

### メモリリークの見せ方
- 直近ウィンドウ (既定 5 分) の RSS に線形回帰をかけ、傾きが閾値 (既定 +1 MB/分) を超えて継続したら「リークの疑い」と警告する。起動直後のウォームアップ (既定 60 秒) は除外する。
- GPU メモリにも同じ判定を適用する。
- 診断パネル (§6.1) に警告として並べる。

### ネットワークの注意点
- **NIC の監視は「PC の外との通信」の監視**と位置づける。対象は外部 API の呼び出しや、他 PC の ROS ノードとの DDS 通信。
- 同じ PC 内の ROS 通信は loopback または共有メモリを通り、物理 NIC には現れない。PC 内の ROS 通信量は、トピック帯域 (§4.3) で見る。
- **監視できるのは roshanavi が動いている PC だけ** (UI に明記する)。他の PC の NIC や UDP の状態は見えない (Lv2 で対応)。
- **接続先のリアルタイム表示**: プロセスごとのソケットを 1 Hz で取得し、接続の開始・終了をイベントとしてタイムラインに流す (接続先ホストは逆引きして表示)。
  - 限界: ポーリングなので、1 秒未満で終わる短い接続は取りこぼすことがある (確実に捕まえるには eBPF / conntrack のイベントが必要。将来の選択肢)。
  - 他ユーザーのプロセスのソケットは root 権限がないと見えない。自分が起動したノードは見える。
- **通信内容**:
  - ROS (他 PC との DDS 通信を含む): パケットではなく、トピックを購読して中身を見る (既存のエコー機能)。
  - 外部 API: 大半は HTTPS で暗号化されており、外から中身は見えない。**本体では中身を見ない** (接続先・時刻・状態のメタデータのみ)。
    - 理由: 通信を中継して覗く機能 (TLS インターセプト) が本体に入っていると、企業のソフトウェア承認やセキュリティ審査で導入を拒否されたり、EDR に検知されたりするおそれがある。企業内でも使えることを優先する。
    - 将来の選択肢 (優先度最低): 本体とは別パッケージ (`roshanavi_inspector`、既定では入らない) として、Launcher で起動したノードに限りローカルのプロキシを経由させる。システムに CA を入れず、そのプロセスにだけ信頼させる。社内プロキシへの多段接続に対応し、認証情報は既定でマスクする。
    - 代替案: 開発者が自分のノードに組み込む小さなロギング用ヘルパー (API 呼び出しの要約を `/roshanavi/api_log` トピックに流す)。通信には介入しないため、審査上の懸念がない。
  - パケットキャプチャ (tcpdump 等) は root 権限が必要なため、標準機能にはしない。
- **UDP バッファ溢れの診断**: RcvbufErrors が増えていて、かつ大きいメッセージのトピックで `dropped` が出ている場合、「受信バッファ不足の可能性。`net.core.rmem_max` の引き上げを検討してください」と診断パネルで案内する (ROS 2 で大きなデータを扱うときの典型的なつまずき)。

### ディスクの安全装置
- 録画中に data_dir の空き容量が閾値 (既定 1 GB または 5%) を下回ったら警告し、さらに下回ったら録画を自動停止する。

## 段階
- **Lv1 (同じ PC)**: psutil (+ pynvml) で 1 Hz 計測する。上の表の全項目を対象とする。
- **Lv2 (複数 PC・複数コンテナ)** ※さらに優先度低 (将来対応。P8 では Lv1 のみ実装): 各マシンで `ros2 run roshanavi agent` を動かし、プロセスごとの統計を `/roshanavi/host_stats` (独自 msg) で publish する。roshanavi 本体はこれを集約し、ホストごとに表示する。
- **GPU (任意)**: NVML (pynvml) が使える環境では、GPU 使用率・GPU メモリと、プロセスごとの GPU メモリを取る。

## 表示
- ライブ通信マップ: ノードに CPU% / メモリのバッジを付け、負荷を色で示す。右ペインに推移のスパークラインを出す。
- 推定で対応づけた値には「推定」の印を付ける。

## シナリオ連携
- `resources` 判定: `{node: /detector, cpu_max: 80, mem_max_mb: 500}`
- `mem_growth` 判定: 一定時間の RSS の増加傾き (MB/分) が閾値以下であること (リーク検出)。
